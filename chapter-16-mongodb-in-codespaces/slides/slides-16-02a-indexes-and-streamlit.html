  .explain("executionStats")

One Title

Python >>>, connected to imdb as on the preceding setup slide:

Plan Examined Returned Time
Before COLLSCAN 12,949,098 47 4,377 ms
After FETCH > IXSCAN 47 47 0.3 ms

Index build: 31.8 seconds. Index size: 227 MB.

Two Conditions

Python >>>, same imdb connection:

list(titles.find({"title_type": "movie", "start_year": 1994}))

Plan Examined Returned Time
Before COLLSCAN 12,949,098 4,248 4,629 ms
After FETCH > IXSCAN 4,248 4,248 11.4 ms

One compound index on (title_type, start_year): 20.6 seconds, 74 MB.

Top Ten by Votes

Python >>>, same imdb connection:

list(ratings.find({}).sort("num_votes", -1).limit(10))

Plan Examined Time
Before SORT > COLLSCAN 1,730,480 344 ms
After LIMIT > FETCH > IXSCAN 10 0.2 ms

An index is already in sorted order, so no sort is needed.

What an Index Costs

Index Build time Size
primary_title 31.8 s 227 MB
title_type, start_year 20.6 s 74 MB
num_votes 2.0 s 9.8 MB

Every insert and update must also maintain each index.

Reading a Plan

Stage What it tells you
COLLSCAN No usable index; every document read
IXSCAN An index was used
FETCH Full documents read after the index
SORT Sorted in memory after reading
LIMIT Stopped after enough results

Rule of thumb: examined far above returned means look for an index.

Python Context: Inspect the Join

Second Bash terminal: repeat cd, .venv activation, and the connection setup; then start Python:

python

At the Python >>> prompt:

from imdb_queries import connect
client, db = connect("imdb")
titles = db.titles
query = {"primary_title": "The Godfather"}

The Page Joins by _id

rows = list(titles.find(query).limit(20))
ratings = db.ratings.find(
    {"_id": {"$in": [r["_id"] for r in rows]}})

Titles and ratings share an _id. The application does the join.
