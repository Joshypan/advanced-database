Database Abstraction

The routes ask for an operation. The database module carries it out.

Source: chapter-04-database-abstraction.md, ../../topic-04-database-abstraction/app.py, database.py, and templates/. Story: same pet application, move database operations behind functions, return named records, follow a create and edit, test the module directly. Structured Query Language (SQL) stays in database.py. Examples are source excerpts with line breaks adjusted; illustrative records are identified.

Why an Abstraction Layer?

A named operation hides the details of carrying it out.

pet = database.get_pet(id)

The route asks for a pet. The module handles the query.

Query details can change while the calling code stays the same.

Abstraction layer: a set of operations between a caller and the implementation it uses. get_pet promises a dictionary or None. Its caller can work with that promise without managing a cursor or converting a database row. Changing the query while preserving the accepted arguments and returned values keeps the route unchanged. One implementation also serves both routes and direct Python tests. Less detail to hold in mind when reading a route. Structured Query Language (SQL) belongs behind this interface.

Single Responsibility Principle

Single Responsibility Principle (SRP): one reason to change.

What changes? Where it belongs
Request handling or page selection app.py
How pets are stored or retrieved database.py

Keep code that changes for the same reason together.

A responsibility is a coherent area of work. A module can have several functions serving that responsibility. app.py handles web requests and chooses responses. database.py owns database operations. A different redirect belongs in app.py. A different query for loading a pet belongs in database.py. These changes have different reasons, so separate modules give each a clear home. Adding a new field can still involve both modules and templates because it changes both storage and the user interface. The principle guides where work belongs; it does not promise that every feature changes only one file.

Two Modules, Different Work

app.py database.py
Read the request Open the database
Call an operation Execute SQL
Render a template Return records
Choose a redirect Commit writes
Hypertext Transfer Protocol (HTTP) requests and Hypertext Markup Language (HTML) responses belong to the web application. Database module works with Python values and stored records. Abstraction gives an operation a name and a calling interface. Same functions can serve a route or a direct Python test. No change to the user's basic create/edit/delete activities.

The Database Interface

Function Result
get_pets() List of dictionaries
get_pet(id) Dictionary or None
create_pet(data) Saved new record
update_pet(id, data) Saved changes
delete_pet(id) Removed record
Result column describes outcome. Write functions return None after committing. Read functions return values to their caller. app.py decides which page to display. The names express what the caller wants without repeating SQL. data contains name, age, type, food, owner. Identifier supplied separately for update and delete.

Preparing the Table

app = Flask(__name__)
database.setup_database("pets.db")
Pet fields
Identity id, name
Description type, age
Care food, owner
setup_database initializes connection, creates table if absent, adds food or owner if missing. type is the field called kind in the earlier example. Food retained, owner added. PRAGMA table_info supplies column names. ALTER TABLE adds a missing column using fixed names from the setup loop. Existing values survive repeated setup; newly added columns start NULL. Fresh table is empty. Sources: https://www.sqlite.org/pragma.html#pragma_table_info and https://www.sqlite.org/lang_altertable.html.

Named Records

connection.row_factory = sqlite3.Row
pets = cursor.fetchall()
pets = [dict(pet) for pet in pets]

pet['food'] and pet['owner'] identify fields directly.

sqlite3.Row supports access by column name. dict(row) produces an ordinary Python dictionary. get_pets returns a list of these. Contrast earlier tuple indexing only to explain why named access helps here. get_pet returns one dictionary. Reference: https://docs.python.org/3/library/sqlite3.html.

Listing Pets

@app.route("/pets", methods=["GET"])
@app.route("/list", methods=["GET"])
def get_pets():
    return render_template(
        "list.html", pets=database.get_pets()
    )

The template chooses the displayed field order.

Two get_pets functions: route in app.py, database function qualified by module name. Template inner loop explicitly lists id, name, type, age, food, owner. Headings use that order. This remains correct when a new column was appended during setup. NULL becomes None, displayed as an empty string. Record id supplies edit and delete links.

Creating a Pet

@app.route("/create", methods=["POST"])
def post_create():
    database.create_pet(dict(request.form))
    return redirect(url_for("get_pets"))

The database function commits before returning.

Create form fields match dictionary keys. request.form values arrive as strings; database function converts age to int with zero fallback. Parameterized INSERT binds name, age, type, food, owner. SQLite supplies id. url_for names the Flask endpoint, not database.get_pets. Browser follows redirect and asks for the list again.

Inside create_pet

cursor.execute(
    "INSERT INTO pet(name, age, type, food, owner) "
    "VALUES (?,?,?,?,?)",
    (data["name"], data["age"], data["type"],
     data["food"], data["owner"]),
)
connection.commit()

The column list determines the parameter order.

Equivalent SQL excerpt after the existing age conversion and cursor creation. Adjacent Python string literals join. Food and owner are independent fields. Parameters handle O'Malley without manually inserting SQL quotes. A test calls create_pet using the same dictionary keys as the route, without submitting a form.

Loading One Pet

cursor.execute("SELECT * FROM pet WHERE id = ?", (id,))
pet = cursor.fetchone()
if pet is None:
    return None
return dict(pet)

A dictionary means found. None means absent.

Body excerpt from get_pet after int conversion and cursor creation. Identifier is a primary key, so fetchone gets the selected record. No row returns None. Route selects error.html with 404 for an absent record. Missing identifier route returns 400. Flask's <int:id> converter provides an integer on the normal edit route.

Saving the Edit

database.update_pet(id, dict(request.form))
return redirect(url_for("get_pets"))

Five replacement values, followed by the identifier.

POST route checks record existence before calling update_pet. Database function converts age, binds values, executes update, commits. Then route redirects. Persistence cycle remains: determine action, load state, take action, save state. Display occurs in edit form and refreshed list. SQL shown with uppercase keywords for readability; same statement as module.

Deleting a Pet

@app.route("/delete/<int:id>", methods=["GET"])
def get_delete(id):
    database.delete_pet(id)
    return redirect(url_for("get_pets"))

The database function deletes and commits.

Existing list link supplies selected id. Flask converts it to integer. Database module executes parameterized DELETE. Route chooses the next browser destination. Same boundary as create and update. Module does not render templates or choose redirects.

Use the function boundary to follow one operation at a time.

Same application behavior, clearer place to find each kind of work. Inspect request values in app.py, then the named function in database.py. Returned dictionaries connect records to templates. Commit completes a write before route responds. Closing example: change food and owner for one pet, follow update_pet, then read that pet back.
