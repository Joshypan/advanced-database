Introduction to Web Applications

A browser interface for the pet database

The earlier script ran a fixed sequence and stopped. This application waits for requests. Same SQLite database operations, now selected by user actions. Story: address and request, route and template, form submission, saved state, fresh display. Source: chapter-03-intro-to-web-apps.md and ../../topic-03-intro-to-web-apps/app.py and templates/. Code excerpts use adjusted line breaks. Simplifications identified with their examples below.

The Pet Application

  • Requests select Python functions.
  • Templates produce browser pages.
  • Forms supply values for database operations.
  • Saved records survive the server stopping.
Browser, Python process, database file. Separate places where values exist. Hypertext Transfer Protocol (HTTP) carries requests and responses. Hypertext Markup Language (HTML) describes the returned pages. Structured Query Language (SQL) expresses database operations. Persistence cycle now spans separate requests rather than one uninterrupted script.

Running Flask

From a working copy of topic-03-intro-to-web-apps:

flask run
http://127.0.0.1:5000/pets

The supplied pets.db holds the existing records.

New environment: python3 -m venv .venv, source .venv/bin/activate, pip install flask. Flask discovers app.py and its app object. Explicit equivalent: flask --app app run. Flask run --port 5001 for an occupied port. Local development server. Keep terminal running, Control-C to stop. Database filename is relative to working directory. Wrong directory can create an empty pets.db without a pet table. This app does not rebuild the database at startup. Reference: https://flask.palletsprojects.com/en/stable/quickstart/.

A Request Calls a Function

@app.route("/bye", methods=["GET"])
def get_bye():
    return "Bye!"

GET /bye receives Bye!

app = Flask(__name__) creates the application. The decorator registers a route. Defining the function does not send a response until a matching request arrives. GET requests a representation. The return value becomes a response with status, headers, and a body. Function names are for Python and endpoint lookup. The route determines the accepted path and method.

A Value in the Path

@app.route("/hello/<name>", methods=["GET"])
def get_hello(name="world"):
    return render_template("hello.html", name=name)
<body>Hello, {{ name }}! (from the template)</body>

/hello/Ada displays Hello, Ada! (from the template)

Excerpt omits the additional / and /hello decorators, which use the default world. The path supplies name as a string. render_template passes it to Jinja. Double braces insert a value. Jinja evaluates on the server. Browser receives completed HTML, not Python or Jinja source. HTML templates automatically escape ordinary inserted strings, so angle brackets in a name display as text. Reference: https://flask.palletsprojects.com/en/stable/quickstart/#rendering-templates.

cursor = connection.execute("select * from pet")

(id, name, kind, age, food)

Each returned tuple becomes one displayed row.

Body excerpt from get_pets, omitting pprint debugging output. rows is a list of tuples. Schema order supplies the tuple positions because SELECT * uses all columns. pprint goes to server terminal, not browser. Query has no ORDER BY, so no promised display order. pets.db contains persistent records; rows contains values loaded for this response. Opening and Submitting a Form

Request Function Result
GET /create get_create Blank form
POST /create post_create Saved pet, then redirect

Same path. Different methods and work.

Opening the form does not insert a record. Typing changes browser input values only. Submitting creates a new request with the form fields. Flask selects separate functions using the method. POST data goes in the request body for this form. GET is for retrieving a representation, not changing stored records. Reference: https://developer.mozilla.org/en-US/docs/Learn_web_development/Extensions/Forms/Sending_and_retrieving_form_data.

Named Inputs Become Form Values

<form action="/create" method="post">
    <input name="name"/>
    <input name="age"/>
    <button type="submit">Create</button>
</form>
data = dict(request.form)

data["age"] arrives as a string.

Shortened form shows only name and age. Full create.html also supplies kind and food, plus labels and a Cancel link. action sets destination. method sets request method. Input name supplies the key, not the nearby visible label. Browser sends age as text. Cancel follows /pets without submitting. Creation binds submitted age directly; update tries int conversion. Neither approach is complete input validation.

Saving the New Pet

connection.execute(
    "INSERT INTO pet(name, kind, age, food) "
    "VALUES (?, ?, ?, ?)",
    (data["name"], data["kind"],
     data["age"], data["food"])
)
connection.commit()

SQLite supplies the identifier.

Equivalent excerpt from post_create. Adjacent string literals join in Python. Parameters keep supplied values separate from SQL syntax. O'Malley works without manually quoting an SQL string. Omitted cursor assignment and unused fetchall: INSERT without RETURNING yields no rows to fetch. execute performs the insertion; fetching does not execute it. Commit completes the transaction. Route next returns redirect(url_for("get_pets")).

After the Save

return redirect(url_for("get_pets"))
Step What happens
POST /create Insert and commit
302 response Redirect browser to /pets
GET /pets Query and display saved records
Post/Redirect/Get. url_for uses the endpoint function name, not a literal path. Redirect response tells browser where to request next. The redirect itself does not render pets.html or transfer the Python rows variable. The subsequent request runs get_pets and reads the saved database state. Refreshing the final page repeats the list request rather than ordinarily repeating the insertion. Browser network tools show these separate exchanges.

The Persistence Cycle in an Edit

Stage Pet application
Determining Action Choose Edit for pet 3
Loading State GET /update/3 reads the record
Taking Action Change fields in the browser
Saving State POST /update/3 updates and commits

Display State can happen anywhere in the cycle.

Edit form displays loaded state. Browser displays typed changes before saving. Redirect displays saved state through a fresh list query. POST handler obtains submitted values and runs UPDATE with four new values and id as parameters. HTTP does not keep one Python function call alive across these requests. The identifier connects the submitted form to its stored record. Restarting the server preserves committed database state, but recreates the in-memory connection and later result objects.

Deletion and Invalid Input

Current example Better behavior
GET /delete/3 deletes Submit a POST to delete
Invalid age becomes 0 Reject it and explain the error
Missing record shows a page Return a suitable error status too
GET should not change stored state. The teaching app uses a deletion link for convenience. A finished version also needs protection against cross-site request forgery, where another site induces an unwanted request. Error template defaults to status 200; missing record normally warrants 404. Existing broad except hides distinctions. Extra @app.route("/update") on both update functions registers GET, including on post_update. POST /update is not registered; saving uses POST /update/<id>. Decorators control routing, not function names. Chapter exercises explore corrections.

Response: A page, a redirect, or an error?

The database preserves state between requests.

Trace a single pet creation or edit end to end when debugging. Browser fields, Python dictionaries, database rows are separate representations. Changes require explicit saving. Global connection with check_same_thread=False disables a thread guard, without making concurrent use safe. Request-scoped connection management is a next refinement: https://flask.palletsprojects.com/en/stable/tutorial/database/. Database abstraction will collect repeated operations behind functions. Closing advice: trace the request and verify the saved record before changing more code.
